The recruiter pipeline view returns all stages, including hired and rejected. For a company that has been using the platform for 12 months, the rejected array may contain thousands of entries. Describe the query performance problem this creates and two pagination strategies that would address it. What is the trade-off of paginating within a stage vs. paginating across all stages?

Returning all stages including thousands of rejected applications creates slow queries due to full table scans and large payloads that consume memory and network bandwidth. To address this, you can either paginate within each stage—fetching rejected applications in chunks with cursor-based pagination—or paginate across all stages by returning only a fixed number of applications total, with a `nextCursor` that continues from the last application regardless of stage. Paginating within a stage gives recruiters focused views (e.g., "show me only rejected applications page 2") but requires separate pagination state per stage, while paginating across all stages is simpler to implement but makes it harder to jump to a specific stage's data.

The applicant view shows upcoming_interview — an interview with outcome = 'pending' and scheduled_at > now(). If a recruiter scheduled an interview for yesterday but never recorded feedback (outcome is still 'pending'), the interview is past but still has outcome = 'pending'. The applicant sees no upcoming interview for this application, which is correct. But the recruiter's pipeline shows no interview either (the latest interview is past). Describe the operational consequence and propose a mechanism to flag overdue interviews.

When an interview passes its scheduled time without feedback, the applicant correctly sees no upcoming interview, but the recruiter's pipeline also shows no interview activity because the latest interview is past—creating a silent failure where the application appears stuck without any visible action item. To flag overdue interviews, add a `flagged_overdue` column or a view that queries `WHERE outcome = 'pending' AND scheduled_at < NOW()`, and display a banner on the recruiter's dashboard showing "3 interviews awaiting feedback" with direct links to the overdue items. This mechanism ensures recruiters are proactively alerted to incomplete interviews rather than discovering them only when reviewing the pipeline.
