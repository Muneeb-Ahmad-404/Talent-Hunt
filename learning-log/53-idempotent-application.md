Yes this is the correct behavior, as the application answers etc should not support updation. If user was allowed to update it would have resulted in confusion, as a recruiter could have judged him based on his previous answers and after the answers change the judgement could end up wrong. An alternate design if you want to support updation is to make an update route, but as mentioned before updation should not be supported and for the current design there is no flexibility.

The idempotency guarantee relies on the UNIQUE constraint at the database level, not on application-layer checks. A developer removes the UNIQUE constraint "to improve INSERT performance" (citing that constraint checks add overhead on every write). Describe exactly what breaks, provide a concrete scenario showing the duplicate state that results, and quantify the actual performance benefit lost by removing the constraint.

The idempotency breaks, now there could be two applications for the same job_id, applicant_id pair. Consider two transactions fired at the same time. Both check for the existance of previous application for the same (job_id, application_id). Now both checks return false and now they move forward and submit the application, without the unique constraint both applications would be listed. THis loss is greater then the little constraint check overhead. This could lead to further problems for the client, as it expects a single application.
