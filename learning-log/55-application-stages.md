The service returns NotFoundError (404) when a recruiter tries to access an application that belongs to another company. A security auditor argues this is still an information leak — a recruiter who enumerates UUIDs can determine which UUIDs are valid application IDs (they get 404, not a different error). Propose a defence against UUID enumeration attacks that does not require changing the 404 response.

The simplest defense is to rely on UUID v4's randomness with 122 bits of entropy, brute-forcing a valid ID is computationally infeasible, making the 404 response safe in practice. To prevent timing leaks, ensure both found and not-found queries take the same time by adding a constant delay on 404 responses to match the typical query duration. Rate limiting and monitoring for burst 404 requests provide additional hardening. Since UUID enumeration is practically impossible, the current 404 behavior is already secure.
