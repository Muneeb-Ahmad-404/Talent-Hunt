The public board endpoint returns 404 for a closed or suspended-company job rather than a different error. A product manager argues applicants who have bookmarked a job URL should see "This job is no longer available" rather than a generic not-found page. Describe two implementation approaches: one that keeps the single error type and one that adds a new response. What are the security and UX trade-offs of each?

For the single error type approach, we would just display a job not found 404 page, no one knows if the job exists or if its closed etc.. The user would understand that the job does not exist anymore and will move on could be a bit pissing for the users though. 
If we try and add a new response we risk exposing to our attackers that a particular job exist in the backend and just not publicly available. So this is a security concern but the user knows whats going on.

The location filter uses ILIKE (case-insensitive partial match). This means searching for location=York would match New York. Explain when partial matching is desirable and when it is problematic for a job board. Propose a data model change that would allow both exact-match and partial-match filtering cleanly.

partial matching is desireable for searching names etc.. or a job post when you are not really sure about the title. But the problem is tradeoff in speed. For a job portal system there are too many jobs and scanning all these is tiresome. The problem with partial search is that if a person starts searching lets say with 'a' there are far too many matches wasting time and resources. A better approach that support both exact and partial match filtering is gini or vector based. It stores indices against specific words for partial search and can help with exact match too with the same indices.
