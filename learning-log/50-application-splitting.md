The service rejects the entire request if any job in jobIds is closed or not found. An alternative is to skip closed/missing jobs (like it skips already-applied jobs) and only fail if ALL jobs are invalid. Compare these two designs on: user experience when a job closes between the applicant viewing it and submitting, consistency of the response shape, and the risk of silent data loss (applicant thinks they applied to a closed job but no row was created).

The "reject all" design fails the entire request if any job is closed or not found, which protects the applicant from thinking they applied to a job that no longer exists but creates a frustrating experience when a single closed job blocks the entire application submission, especially if they selected multiple jobs. The "skip invalid" design allows partial success—applying only to valid, open jobs while skipping closed or missing ones—and only fails if every job in the list is invalid, which feels more user-friendly but risks the applicant assuming they applied to all jobs when some were silently skipped. I would choose the "reject all" approach because it provides clear feedback to the applicant about which specific jobs failed, preventing silent data loss and ensuring the applicant is fully aware of what was and wasn't submitted.

The answers for each job are stored in applications.answers (JSONB). A recruiter's screening question asks "Do you have a valid driver's license?" with a boolean answer. The applicant submits {"answer": true}. Six months later, the recruiter changes the question to "Do you have 3+ years of driving experience?" The stored answer now looks like a "yes" to a completely different question. Describe the data integrity problem and propose a schema that makes stored answers self-describing.

When the recruiter changes the question text from "Do you have a valid driver's license?" to "Do you have 3+ years of driving experience?", the stored boolean answer true becomes semantically incorrect because it now represents a "yes" to a completely different question, making the historical data meaningless and potentially misleading for hiring decisions. To solve this, store answers as self-describing objects containing both the question text and the answer at the time of submission, using a schema like { question: "Do you have a valid driver's license?", answer: true, questionId: "q_123" } so that even if the question changes later, the original context is preserved for auditing and review. This approach maintains data integrity and allows recruiters to see exactly what was asked and answered when the application was submitted, independent of future changes to the screening form.
