The shortlist limit is enforced with a COUNT query before INSERT. This check is not atomic — two concurrent requests from the same applicant could both pass the count check and both insert, briefly exceeding the limit of 100. Describe the full sequence of events that produces this race condition. Then propose a PostgreSQL-level solution that makes the limit truly atomic, without adding a COUNT query.

The race condition occurs when two concurrent requests from the same applicant both read the current shortlist count as 99 before either insert completes, allowing both to proceed and insert a job, exceeding the 100 limit. To make this atomic without a separate COUNT query, you can use a PostgreSQL trigger that runs on INSERT and checks the count within the same transaction, raising an exception if the limit is exceeded, or use an advisory lock to serialize shortlist modifications for that applicant. The trigger approach is cleaner because it enforces the rule at the database level, ensuring that no matter how many concurrent requests arrive, the limit is never breached.

The shortlist query returns jobs that are now closed. Consider two designs: (A) filter out closed jobs at query time so the shortlist only shows open jobs, or (B) return all jobs with their current status. Compare these on: user experience when a previously shortlisted job closes, data integrity (does the shortlist accurately represent the applicant's intent?), and the complexity of the query.

Design A filters out closed jobs at query time so the shortlist only displays open positions, keeping the list clean and focused only on currently available opportunities, but it can confuse applicants when a job they saved disappears without explanation. Design B returns all jobs with their current status, showing a "Closed" or "Expired" badge on closed positions, which preserves the applicant's full shortlist history and provides clear context about why they can no longer apply. I would choose Design B because it offers better transparency and data integrity—applicants can still see their original intent and understand the current state of each job—while the filtering of closed jobs can be handled client-side with a toggle for "Show only open jobs."
